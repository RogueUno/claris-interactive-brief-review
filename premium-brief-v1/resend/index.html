Resend — API Security

Consultant: Chase MillerFirm: vCISO.comBooking: “Interested in discussing API security.”

Executive Readout

Resend’s public security surface already answers several low-value discovery questions. It documents SOC 2 Type II, annual third-party penetration tests, AES-256 at rest and TLS 1.3+ in transit; its API access surface spans full- or send-only API keys, OAuth 2.1 + PKCE with dynamic client registration, signed webhooks, and a hosted remote MCP server with OAuth/Bearer authentication [E5] [E1] [E2] [E3] [E4]. The booking itself says only “Interested in discussing API security.” The call needs to resolve two things quickly: which trust boundary is actually in scope, and what result the prospect wants from outside help.

Signals That Matter

1. Multiple credential models, not one generic API-auth surface

Full- or send-only API keys coexist with OAuth 2.1 + PKCE and dynamic client registration. [E1] [E2]
Call implication: scope the credential model first. Static-key permissions and delegated OAuth access are materially different review surfaces.

2. Webhooks are a separate inbound trust boundary

Endpoint-specific signing secrets and Svix signature/timestamp/id headers are documented for authenticity and replay protection. [E3]
Call implication: if webhooks are in scope, skip “do you sign webhooks?” and establish what needs review in the verification/consumption path.

3. MCP adds an agent-facing access surface

Resend operates a hosted remote MCP server with OAuth and Bearer-token connection options. [E4]
Call implication: agent access is a distinct trust boundary worth checking in scope; it is not evidence that MCP caused the booking.

4. Baseline assurance is already substantial

SOC 2 Type II, annual third-party penetration testing, AES-256 at rest and TLS 1.3+ in transit are public. [E5]
Call implication: a generic maturity/SOC 2 opener is low-value. If they want independent validation, establish what needs validating beyond the assurance work already performed.

Hypothesis Worth Testing

Newer delegated / agent access may be part of scope

OAuth 2.1 and remote MCP create distinct delegated-access boundaries. This makes them worth including among the scope options—not a conclusion about why the meeting was booked. [R1]

Call Plan

  1. Identify the exact API/security surface.
  2. Identify the required outcome.
  3. Map the confirmed combination to the consultant’s service catalog; do not pitch before both are clear.
Avoid early: SOC 2/readiness discovery that first-party evidence already answers; any statement that OAuth, MCP, webhooks or a vulnerability caused the booking.
